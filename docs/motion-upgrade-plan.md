# 动效与观感优化方案（2026-10-06）

> 2026-10-07：项 1／2／3／4／6 已按本文推荐项实施完毕，实测数与缺陷注入见文末第 7 节。本文第 1~3 节保留"改前"的量数，作为对照。

本轮只出方案，未改任何产品代码。三条感觉全部换成了可复跑的数，来源是本轮新增的三支探测：
`node scripts/probe-motion-live.mjs`（各氛围各机位的时钟与连拍）、`node scripts/probe-lamp-oscillation.mjs`（夜景换窗的时间序列与净贡献）、`node scripts/probe-night-lamp-wiring.mjs`（四层亮窗各自的屏幕代价）。

## 0｜一句话结论

白昼与日落画面里那 1,981 辆车和 1,244 个行人不是没做，是被**一个布尔顺手关掉的**——`trafficVisible` 同时管着"光带亮不亮"和"近场走不走"两件事，白天前者为假就把后者一起带走了。夜景那四层窗灯在算、也在换，但它的设计是"出去几格进来几格"，总量守恒，加上每栋每圈只换 1 格，所以眯眼看整面墙就是"没动"。两件事的修法不一样：前者是拆门控（结构性缺陷），后者是换可见性的载体（观感取向，需要裁定）。

## 2｜成因（代码位置与关键常量）

1. **白天近场冻结**：`src/map.js:544` 的 `trafficVisible` 由 `lightTraffic(lit)`（555-567）赋值，`lit` 只在夜景且非高度视图时为真。它被用在三处：光带三层可见性（557，正确）、车灯 `setTrafficLamps`（560，正确）、以及**动效循环里"近场要不要推进"的闸门**（`src/map.js:1046`，这一处是错配）。另外 561-567 在 `lit` 为假时把 `motion.life` 归零并 `advance(0)`，所以白天连"停在哪儿"都是出厂那一格。
2. **行人不在默认机位**：`src/traffic-life.js:448` `people.visible = viewZoom >= WALKER_MIN_ZOOM`，而 `WALKER_MIN_ZOOM = 16.5`（216 行）。默认机位是 15.5，所以"行人不动"实际是"看不见行人"；这条理由（1.75 m 的人在 15.5 级不到一个像素）写在 `tests/browser.spec.js:4098` 的断言注释里，界面与文档没有。
3. **换窗看不见**：`src/facade.js:349` `LAMP_SWAP_SHARE = 0.14`，配合 `swapCells`（408-418）"出去几格进来几格"的守恒，一档 2~5 格里每圈只翻 1 格；`src/map.js:335-339` 两层的透明度是 `weight` 与 `1 − weight`，两张图亮格数相等 ⇒ 整墙亮度恒定。周期 `LAMP_PERIODS_MS = [11000, 17000]`，`LAMP_TRANSITION = 0.26`（一圈里只有 26 % 的时间真的在过渡）。

## 3｜优化项

### 项 1｜白昼与日落让车与人走起来（拆 `trafficVisible`）

- **改法**：把"近场要不要推进"从"光带亮不亮"里拆出来。新增一个 `nearFieldRunning = motion.on && lens.mode !== 'height' && 近场在屏内`，`src/map.js:1046` 那道闸门改读它；`lightTraffic(lit)` 只负责光带可见性与车灯，**"归位到出厂那一格"只在动效从开变关的那一次做**，不再在白天每拍归零。关掉动效仍回到出厂帧这一条不许破（#114 的收口成果）。
- **判据**：白昼与日落各测一次 `motionStatus().lights` 在 2.4 s 内的差 > 0；夜景保持现状；减少动态效果下三个氛围都 == 0（`tests/browser.spec.js:4249` 已钉，不许改）。
- **注入（三条，各钉一条判据）**：① 把 1046 的闸门去掉（永远推进）→ 减少动态那条必须红；② 把 `nearFieldRunning` 写死 false → 白昼那条必须红；③ 把"只在关闭那一次归位"改回"每拍归零" → 夜景"车在走"必须红（每拍归零就等于不动）。
- **代价**：白天每拍多跑 1,981 + 1,244 个实例的位置更新。要实测：五分钟连续操作段的帧间隔 p95／p99 与最长帧（现值 p95 16.7 ms／p99 16.8 ms／最长 33.4~50.1 ms），**门槛不放宽**，超了就把近场推进从 120 ms 一档降到 240 ms 一档并写明理由。
- **撤销**：`src/map.js` 恢复 1046 读 `trafficVisible`、恢复 561-567 的无条件归零，删两条新判据与对应注入。

### 项 2｜行人在默认机位要么给看见，要么明说

- **A 档（推荐）**：不改阈值，把"要到 16.5 级才出现行人"写进界面说明与 README 的动效段，并在 `nearTraffic()` 的读数里带上 `walkerMinZoom`，让验收与使用者都能看到为什么这块画面没有人。理由：1.75 m 的人在 15.5 级约 1.1 px，硬放大就是噪点，V7 那条"分辨率地板"的理由仍然成立。
- **B 档**：把 `WALKER_MIN_ZOOM` 降到 15.5，同时给 `trafficScale` 一个下限倍率。代价：这块画面会多出 1,244 个亚像素点，眯眼测试（第 4 档亮窗那一档）可能被判成噪声，需要重跑亮度预算表。
- **判据**：A 档钉"文案存在 + 读数带阈值"；B 档钉"15.5 级行人像素数 > N 且环绕 15 s 帧率不掉到 55 以下"。
- **撤销**：A 档删文案与字段；B 档改回常数并删新增判据。

### 项 3｜让"换窗"真的看得见（需要裁定）

总量守恒是设计承诺（每栋楼的窗数由高度档钉住），所以**在"一格级"上再怎么加大幅度都不会被看见**——要看得见，只能把变化放到整栋级或亮度级。三个选项：

| 选项 | 做法 | 限制 |
|---|---|---|
| C（推荐） | 保留全城一格级的换窗，另加一小撮**整栋级**的明灭：按 OSM id 取一个互质的模（例如 1/23 的楼）在 11 s／17 s 周期里整栋换亮↔灭一档 | 与 V6-3"不整楼闪"的裁定有张力，需要把口径改成"少数整栋慢换、多数逐格微调"；亮度预算表第 4／4b 档要复量 |
| A | 把 `LAMP_SWAP_SHARE` 从 0.14 提到 0.4，并把 `LAMP_TRANSITION` 从 0.26 放宽 | 只改"哪几格"的密度，总量仍守恒；实测净贡献从 3 % 最多到 8 %，仍可能被车流噪声盖住；每档 2~5 格时 `round(2 × 0.4) = 1`，矮楼根本换不动 |
| B | 打破总量守恒：让 set 1 比 set 0 少亮 1~2 格，整墙亮度随之呼吸 | 直接推翻 V7 那条"窗数由高度档钉住"的承诺，`tests/facade*.test.js` 里钉"换窗不换量"的断言要整条反转，属于改口径不是改参数 |

- **判据（ whichever 选定后）**：`probe-lamp-oscillation.mjs` 的净贡献从 3.0 % 提到 ≥8 %，且墙面平均亮度全距从 1.0 提到 ≥3.0；同时"整栋级明灭"要钉**不许出现整城同亮同灭**（同一帧里亮着的楼数在周期内变化 ≤ ±5 %）。
- **代价**：C 档要新增一组贴图或一个 alpha 档（图集多一行）；A 档几乎零成本；B 档要重排 V7 的判据。
- **撤销**：三项都是参数或一档贴图，各自回滚一行常数／一层。

### 项 4｜日落档是三个画面里最"死"的

连拍每 600 ms 只变 1,408 ~ 3,475 颗（白昼 38,599、夜景 132,954），因为日落的江面贴图滚动幅度小、光带与近场又都不参与。项 1 落地后日落会拿到与白昼同等的车流推进，但**白昼那 38,599 颗主要来自江面滚动与塔身变色，不是车**——所以日落不一定追得上白昼，这一项要单独给数。判据：项 1 落地后复测日落连拍，若仍 < 白昼的 60 %，再单独动"日落江面高对比一档"（那是观感取向的改动，需要点头）。

### 项 5｜新引擎（`?engine=three`）的动效对等

新引擎目前**没有**车流、行人、壳体发光、江面波光，灯火只有静态那一组窗格（图集只画了 `set 0`）。两引擎的"动"现在完全不对等，Phase 4 做业务回迁时这里一定会红。已记为待办 #160（换窗与呼吸进图集）与 V8 Phase 3（车流、行人、壳体、波光）。建议顺序：先在新引擎接**车流与行人**（现版已有确定性算法，可逐字节对照），再接换窗呼吸。

### 项 6｜度量口径要补一条轨

像素法量不了 pattern 图层：改一次样式就触发 MapLibre 重图集，像素差量到的是渲染器的抖动而不是这一层的贡献。本轮的证据很直白——**把 `building-lights` 那两层关掉、把 `building-lights-2` 那两层关掉、把 `building-glow` 关掉、把四层一起关掉，四次读到的变动像素数都是 11,496 颗**（四层一起关也只多到 11,498），不同层的贡献不可能恰好相等；同一件"把权重从 1 钉到 0"的测量，两次分别读出 0 颗与 573,436 颗。所以这类判据一律走两轨：**计数器轨**（`motionStatus()` 的 `lights`／`lampTicks`／`lamps`）证明"在算"，**时间序列轨**（不改样式、连拍一整周期，再拿同权重相邻帧做噪声地板相减）证明"看得见"。缺一条就算没验。

### 项 7｜性能护栏

项 1、项 3、项 5 都会往循环里加东西。本轮已有的数：现版路径首帧上传 324 张灯层贴图 + 9 张立面 + 3 张江面；新引擎每桶四层、24 发 draw call、277,536 三角、60 fps、最长帧 16.8 ms。加完之后的复测清单：五分钟连续操作段、学校环绕 15 s、`night-budget-meter`、以及新引擎的 `counts()`。

### 项 8｜V5 遗留的三条观感欠账

猎德大桥在默认机位画框外；1 km 近场车流未做降级；塔身单色↔彩虹两档之间无过渡。都不在本轮主题线上，但和"动"一样属于观感欠账，建议排在项 3 之后一并处理。

### 项 3 的实现里踩到的一条硬限制

第一版 C 档把"整栋慢灭"写成 opacity 乘子（`['*', alpha, 1-0.9+0.9*权重]`，乘子按 `osmId % 17` 选分支），画面当场变成**零变化**——因为 `fill-extrusion-opacity` 不是数据驱动属性，表达式里出现 `['get', ...]` 会被样式校验器**整层丢掉**（error 事件、不抛异常、图层仍在样式里、console 零条可读）。这正是 README 里"衰减只能进贴图"那条的同一根因，本轮再验一次：**逐栋的判断只能挂在 `fill-extrusion-pattern` 上**。所以"跟着权重慢灭"最终等价于"交叉淡的另一手里给它一张全灭的图"，而权重=1 时那一手的 opacity 精确为 0，出厂帧逐字节不变。晕跟着灭则只能靠**拆层**：`building-glow` 留给多数（常量），`building-glow-breath-0/1` 各带一组的权重——注入"把晕的权重拿掉"后成簇度从 290 掉到 112，说明这一档的连贯度大半是晕给的。

### 项 4 为什么不照 60 % 那条改

日落的时钟与白昼已经同拍（20/2.4 s），差的不是"没在动"而是"动的东西对比低"：连拍里日落每颗变动像素的平均变化量是 151~158，白昼是 74~84——**单颗更亮，颗数更少**。少的这一半来自江面：日落的水是 V5-2／V5-9 有意压暖压平的低对比档，滚动同样的行数，落进阈值的像素就少一半。要追平白昼只能动那两档的观感取向，本方案自己写明"需要点头"，所以这里不改，只把数留下。另：连拍序列最后一对反复读到 61.6 万颗（两次独立运行都在同一位置），量级是整幅重绘，判定为一张底图瓦片落位造成的探测噪声，不计入判据。

### 这一轮踩到的一条：three 的程序缓存键不看着色器源码

亮窗与光晕两张材质的参数**一模一样**（同一份图集配置、同一种加色混合、同样不写深度），只有 `onBeforeCompile` 塞进去的那段片元不同。three 拼程序缓存键时只看参数，于是第二个材质直接复用第一个编译好的程序——亮窗拿到的是光晕那份片元，`lampAltColumn` 与整栋慢灭那两行代码根本没进 GPU。症状最难认：**把列偏移从 9 改成 4.5，画面零变化**（不是变暗、不是变花，是一颗都不动）。补上 `material.customProgramCacheKey = () => 'lamp-' + mode` 之后，同一处改动在同一机位动了 **4,175 颗**像素。

这条也解释了一次假绿：上一版引擎判据的 `moved > 800` 比缺陷值（1,077）还低，注入"两手册同一列"照样绿。门槛是量出来的，不是估出来的——三张注入表跑完才敢写 1,500 与 400。
